## 1. 项目概览

### 1.1 项目目标

CCS_dev 是一个面向多异构智能体的指挥与控制系统，核心目标是：

- 在地面站统一管理无人机、AGV、机器狗等异构设备。
- 通过 MQTT、UDP 和视频链路实时获取设备状态、遥测、任务和视频信息。
- 管理、显示、生成、下载和融合 PCD/PGM 地图。
- 创建任务、编辑航点、检查任务可执行性，并向端侧设备下发和监测执行状态。
- 支持单机建图、多机联合建图、地图重定位和指控大屏实时态势展示。
- 将地面站通用逻辑与不同设备的 ROS 功能包、传感器和运动控制适配隔离，便于扩展设备型号。

### 1.2 系统边界

系统由两部分组成：

1. **地面站**：Windows/Python/PySide6 应用，负责 UI、设备配置、地图仓储、任务仓储、协议服务、数据展示和操作调度。
2. **端侧工作空间**：Ubuntu + ROS 的设备功能包集合，负责传感器采集、状态桥接、视频推流、遥测发送、建图、重定位和任务执行。

地面站不直接依赖某一种设备的 ROS 内部实现。端侧通过稳定的 MQTT、UDP、视频和建图/任务协议向地面站提供能力，设备差异主要由 profile、话题映射和适配器处理。

### 1.4 数据真值边界

- MQTT：设备在线摘要、心跳、电量、任务摘要、FCU/上位机连接健康和飞行/运行模式。
- UDP 14560：高频位姿、IMU、点云接收状态和传感器状态，主要用于实时显示。
- UDP 14561/14562：实时建图控制、地图成果和 PCD/PGM 分片传输。
- UDP 14563/14564：任务控制、任务反馈和执行状态，是任务执行真值来源。
- SRT：视频媒体链路，不承担设备在线或任务状态。
- 地图位姿与本地 odom 位姿不能直接混用；地图页面显示应依据当前设备 profile 和已建立的 TF/重定位关系。

## 2. 设计目标与原则

### 2.1 主要设计目标

- **统一数据模型**：UI 只消费 `DeviceSnapshot`、地图模型和任务状态，不直接操作 MQTT/Paho、UDP socket 或 ROS 话题。
- **设备可扩展**：设备 ID、IP、话题、frame、图标、标记形状、能力和端侧包通过配置/profile 管理。
- **协议可靠性**：对 schema、设备 ID、序列号、CRC、压缩长度、来源 IP、分片完整性和超时进行校验。
- **运行可诊断**：首页展示子系统状态，设备详情保留分级日志，端侧脚本保存 PID、日志和备份。
- **失败可恢复**：配置写入采用临时文件原子替换；地图删除进入 `.trash`；建图/任务/视频流程支持停止、重试和清理。
- **低风险联调**：端侧部署前备份，真机测试默认不发送非零速度；视频和可选服务故障不应拖垮基础遥测服务。
- **可验证交付**：每次功能迭代同步版本、README、CHANGELOG、开发笔记、接口文档和回归测试。

### 2.2 关键技术决策

- 地面站采用 PySide6，页面由统一 `MainWindow` 和 `QStackedWidget` 管理。
- 早期先用模拟数据建立 UI 和 ROS1/ROS2 适配边界，再逐步替换为 MQTT/UDP 实时数据源。
- MQTT 地面站使用内嵌 `amqtt` Broker 和 `paho-mqtt` 订阅器，Broker 与订阅器运行在线程中，消息通过 Qt signal 回到主线程。
- 高频遥测与 MQTT 设备摘要分离，避免高频数据重建设备卡片和污染静态配置。
- 视频链路从 RTSP 迁移到 SRT：端侧 GStreamer 作为 Listener，地面站使用支持 SRT 的 FFmpeg Caller。
- 地图文件采用目录仓储，而不是把大点云存入单一 JSON；地图元数据与 PCD/PGM/YAML 分离管理。
- 地图融合算法采用可导入 Python 插件，并保留 NumPy RANSAC、Open3D ICP 等样例。
- 建图、重定位、任务流程均采用 session/request ID、状态机、超时、重试和显式 abort/stop 语义。
- 端侧按设备 profile 组织部署，统一启动脚本只管理本次脚本启动的进程，并在退出时逆序清理。

### 3.5 任务、建图和重定位

#### v0.16.0/v0.16.1 遥控建图与会话隔离

- 端侧建图检查 Livox 点云/IMU 类型、frame、新鲜度和有限值。

#### v0.18.0 点云传输可靠性

- 根因：单帧点云约 164 KB，被拆成百余 UDP 分片突发发送，接收缓冲不足且没有补包机制。
- 地面站接收缓冲提升至 4 MiB；不完整帧 350 ms 后请求缺失分片，最多重试 3 次。
- 端侧缓存最近 3 帧，支持 `request_cloud_chunks`；继续校验 CRC32、zlib 长度和坐标有效性。
- 增加强制结束，发送 `abort_mapping`，停止 FAST-LIO、清理订阅和缓存，不生成不完整地图成果。

## 5. 关键问题、根因与解决办法

| 问题 | 根因 | 解决办法 | 验证结果 | 遗留风险 |
|---|---|---|---|---|
| MQTT/UDP 被识别为乱序帧 | 端侧重启后序列归零；QoS 1 重复帧；旧会话消息迟到；设备 ID 大小写不一致 | 引入 `session_id`、会话隔离、重复帧静默处理、presence 兼容重置和标准设备 ID 映射 | v0.16.1 相关测试通过 | 多设备长时间重连仍需压力测试 |
| 高频数据已收到但 UI 不显示 | Go2 launch 写死旧地面站 IP；启动脚本未传专用 profile，回退到错误话题/设备 | 显式传递 `device.yaml`、`udp_telemetry.yaml`，目标地址配置化 | 全量约 196 项测试通过 | 新设备必须检查 profile 和 descriptor hash |
| 点云 UDP 分片丢失 | 单帧分成百余个 UDP 分片，socket 缓冲不足，没有补包 | 接收缓冲 4 MiB、缺片请求、最多 3 次补发、端侧缓存 3 帧 | 端侧 38 项和平台 8 项相关测试通过 | 仍需不同网络质量下的实机压测 |
| RTSP 重新连接无法起播 | FFmpeg 退出语义误判、H.264 参数集/时间戳和取消竞态 | 会话取消重试、baseline Annex-B、周期 SPS/PPS、独立 PTS/DTS、插件检查 | 161 项全量和 15 项专项测试通过 | RTSP 已被 SRT 替代，历史兼容代码需继续隔离 |
| SRT 地面站无法播放 | Windows PATH 无 FFmpeg 或 FFmpeg 不带 libsrt | 安装带 `--enable-libsrt` 的 FFmpeg；启动时搜索 PATH、用户变量和本地目录 | FFmpeg `srt_input=True` | 其他账号/机器需重新安装并验证 |
| 融合算法跨设备部署失败 | 运行时对象仍携带旧设备绝对路径，Windows/POSIX 路径解析不兼容 | 注册表只保存相对文件名；运行时按算法 ID 从当前安装目录重解析；迁移旧路径 | v0.13.2/v0.15.1 路径测试通过 | 发布包仍需验证全新目录安装 |
| PGM/PCD 坐标不一致 | WheelTech 实际分片为 `odom`，地面站默认按 `lio_odom` 校验 | 增加设备级 frame profile；frame mismatch 保留原错误并自动、可重试、幂等 abort | 33 项协议/服务回归通过 | WheelTech 仍需真实接收 3 个分片验收 |
| 地图选点坐标不准确 | VisPy 逆投影返回齐次坐标，缺少 `w` 除法且未处理 PGM yaw/原点 | 使用完整投影矩阵和 `z=0` 射线求交，按 PCD/PGM 边界限制 | 全量 199 项测试通过 | 真实不同 DPI/显卡仍需人工复核 |
| VisPy `Line` 冻结属性异常 | 将 `_ccs_has_trail` 动态写入 Frozen visual | 在 viewer 内维护 `_trail_visibility` 字典，visual 只保存图形属性 | 地图 overlay/picking 24 项通过，提交 `c50cca2` | 其他第三方 Frozen 对象不得动态扩展属性 |
| 建图失败后端侧仍运行 | 地面站进入 failed 后缺少统一 abort/资源释放 | 强制结束、自动 abort、session/进程/PID 清理和状态机终态释放 | Scout 清理通过；WheelTech 增加保护 | 需持续测试断电、网络中断和重复启动 |
| 任务启动慢 | 平台 `group_start_delay_seconds` 为 30 秒 | 调整为 3 秒并加入端侧 ready 前航点可通行性检查 | 端侧 30 项、平台 10 项通过 | 真实 move_base 参数仍需设备级验证 |
| 任务航点执行失败 | waypoint 2 位于 PGM 未知区域，`GlobalPlanner/allow_unknown=false` | 返回 `WAYPOINT_NOT_TRAVERSABLE`；运行期返回 `NAVIGATION_PLAN_FAILED` 并保留原始状态 | 已部署 v0.4.3/v0.22.2 | 需要在有效自由区域重新执行任务 |
| 端侧启动误报成功 | 旧脚本只检查 ROS 话题存在，不检查是否有真实消息 | 关键传感器改为必须收到实际消息，否则失败并清理 | 脚本及测试已更新 | 各设备 profile 的消息 freshness 阈值需统一 |
